PRD — Debt Collection Workflow

Product requirements for the qualification engine and BPMN orchestration of workflow-service: how an incoming debt file is qualified (DMN) and routed to a dedicated collection process (BPMN).

1. Executive Summary

When a debt file enters the platform, it must be qualified and routed to the right collection workflow automatically — without any human pre-screening and without any numeric credit score.

This PRD describes the debt-collection vertical implemented by workflow-service (BPMN engine) and segmentation-service (DMN engine):

  • Qualify — an incoming debt file is analysed across six categorical dimensions (EPIC 1–6) plus reachability, and classified into one of eight qualifications (EPIC 7).
  • Route — each qualification starts its dedicated BPMN collection process (EPIC 8): reminder, phone collection, escalation, pre-legal, legal, update-customer-info, close-file or info-research.
  • Track — every decision is persisted as process history; the outcome (qualification, segment, strategy, status) is returned to the caller.
Key design decision There is no numeric scoring. Qualification is categorical, driven by business rules that live in a Flowable DMN decision table — so rules can change without redeploying code.

2. Problem & Business Context

Creditors (banks, lenders) need to recover unpaid debts while spending as little human effort as possible on routine cases. The collection department handles thousands of files; each must be triaged by severity and handled with the appropriate intensity:

  • A first missed instalment needs a friendly reminder (SMS/email).
  • A second contact needs a phone call task.
  • A broken payment promise needs reinforced follow-up.
  • Serious cases escalate to the pre-legal or legal department.
  • Blocked files (missing client info, unreachable client, already-paid debt) need dedicated handling.

The problem: manual triage does not scale, and ad-hoc Java code makes the routing rules invisible and hard to change. The solution: an executable decision model (DMN) that qualifies every file, wired to an executable process model (BPMN) that applies the right collection strategy — both versioned, auditable, and tenant-isolated.

4. Business Scenario — “The unpaid loan”

A borrower stops paying their instalments. The platform qualifies the file and routes it through the collection workflow — step by step, with the exact process names found in the repository.

4.1 Story

Karim has an active consumer loan (contractStatus = ACTIVE_CONTRACT). He misses his first instalment: the bank creates debt file DEBT-2026-00042. At intake the system only knows debtId and customerId; every behavioural dimension is left unset. The service applies safe categorical defaults (buildVariables in CollectionWorkflowService): CLIENT_INFORMATION_COMPLETE, ACTIVE_CONTRACT, OPEN_DEBT, GOOD_PAYMENT_HISTORY, FIRST_CONTACT, NONE, reachable = true.

5. Qualification Engine — EPIC 1–7

The engine qualifies a file from six categorical dimensions plus reachability. No dimension is numeric; each describes the file in business terms (StartCollectionProcessRequest).

EPIC 1 — Client information

CLIENT_INFORMATION_COMPLETE · CLIENT_INFORMATION_INCOMPLETE

EPIC 2 — Contract status

ACTIVE_CONTRACT · SUSPENDED_CONTRACT · TERMINATED_CONTRACT

EPIC 3 — Debt status

OPEN_DEBT · PAID_DEBT · PARTIAL_PAYMENT

EPIC 4 — Payment history

GOOD_PAYMENT_HISTORY · IRREGULAR_PAYMENT_HISTORY · NO_PAYMENT

EPIC 5 — Collection stage

FIRST_CONTACT · FOLLOW_UP · MULTIPLE_FOLLOW_UPS

EPIC 6 — Payment promise

NONE · PROMISE_ACTIVE · PROMISE_KEPT · PROMISE_BROKEN

Plus the boolean reachable — whether the client can currently be reached (EPIC 7, case 6).

5.1 Optional inputs with safe defaults

All six dimensions are optional in the request. The service fills each missing dimension with a safe categorical default (buildVariables), so callers that only know the debt and customer still get a correct, conservative qualification.

5.2 Facts-resolution seam (M4)

SegmentDebtDelegate does not read the dimensions straight from the request: it asks CollectionFactsResolver, which aggregates one provider per EPIC (ClientInfoProvider, ContractStatusProvider, DebtStatusProvider, PaymentHistoryProvider, CollectionStageProvider, PromiseStatusProvider). Today every provider is a stub that echoes the provided value; tomorrow each can call its business service without touching the BPMN.

5.3 DMN with local fallback

The delegate calls segmentation-service (POST /api/v1/segmentation/execute). If the DMN call fails for any reason (service down, timeout, empty answer), the delegate falls back to qualifyLocally — the same rules mirrored in Java — so the process never stops because the decision engine is unavailable. qualificationSource (DMN/LOCAL) records which path produced the qualification. This never-throw-on-DMN-failure contract must be preserved.

5.4 Derived segment

segment is derived in Java, not in the DMN: HIGH_RISK = {LEGAL, PRE_LEGAL, PROMISE_BROKEN}, everything else is LOW_RISK. The BPMN gateway routes on qualification, not on segment.

6. Business Rules — the DMN

The qualification rules live in debt-segmentation.dmn (decision collectionQualification, hitPolicy=FIRST): rules are evaluated top to bottom and the first match wins — the most blocking / escalating case first. The local fallback in SegmentDebtDelegate.qualifyLocally mirrors the same priority order.

Why a decision table? The rules are the part of the system the business changes most often (thresholds, priorities, new cases). In a DMN table they are versioned data, reviewable by non-developers, and deployable independently — no Java recompilation. The Java fallback exists only for resilience, not as the source of truth.

7.1 Why strategy/status/workflow live in the BPMN

Each sub-process contains a single service task running the shared ApplyStrategyDelegate, configured via flowable:class + flowable:field string injection (strategy, status, workflow literals declared in the BPMN XML). The per-qualification behaviour is therefore declared in the model, not duplicated across Java classes — changing a strategy is a BPMN change, not a code change.

Do not “Spring-ify” ApplyStrategyDelegate It is intentionally not a Spring bean: Flowable instantiates a fresh instance per execution so field injection is safe. In contrast, validateDebtDelegate and segmentDebtDelegate are wired by bean name (flowable:delegateExpression="${...}" ↔ @Component("...")) — renaming one without the other silently breaks deployment. SelectStrategyDelegate is an orphan bean referenced by no BPMN: do not wire it in.

8. Technical Architecture

Two Flowable engines are deliberately split across two services: BPMN lives in workflow-service (port 8094), DMN lives in segmentation-service (port 8092). No other service may depend on Flowable. The API Gateway (port 8080) fronts the platform; tenancy is mandatory on every call (X-Tenant-Id), JWT validation is optional (SECURITY_ENABLED=false by default).

8.1 Schema ownership

  • Flowable engine tables (ACT_*) are created and upgraded by the engine itself (flowable.database-schema-update: true). Never write Flyway migrations for them.
  • Flyway owns only business tables — currently a single outbox_event table (V1__baseline.sql).
  • ddl-auto: validate everywhere; never switch to H2 or ddl-auto: update.

8.2 Two package roots, on purpose

Service code is com.mercure.recouvrement.workflow, shared-kernel is com.deptcollector.shared — both scanned via WorkflowApplication scanBasePackages. Do not “fix” the mismatch.

10. Non-Functional Requirements & Invariants

  • Tenancy is mandatory: every request carries X-Tenant-Id and TenantContext.getRequiredTenantId() guards every endpoint. The synchronous /collection/start starts the instance tenant-less (BPMN auto-deploy) and keeps the tenant as a process variable for traceability; the idempotent POST /processes starts with an explicit tenant id and dedupes by tenant. All read queries (tasks, history, jobs, timers) are tenant-filtered.
  • Correlation: X-Correlation-Id is propagated to segmentation-service and carried in logs (%X{correlationId}).
  • Resilience: DMN failure never blocks the process (local fallback).
  • Consistency: decision logic lives in BPMN delegates and the gateway — never in the service or controller.
  • Observability: Actuator health probes + Prometheus endpoint; history-level audit.
  • Testing: the only test (WorkflowApplicationTest) is a context-load check needing reachable Postgres with the Flowable schema — no H2, no Testcontainers. Do not add H2 as a shortcut.
  • Extensibility: current processes have no user tasks and no timers — everything is synchronous. The tasks/timers/incidents/jobs endpoints and async-executor-activate are operational tooling for when waited/timed steps are added.

12. Out of Scope / Backlog

  • Full legal workflows, multichannel reminders (SMS/email/courier integrations), predictive scoring / AI.
  • Human tasks and timers/SLA in the current BPMN (tooling exists, models do not yet use them).
  • Multi-engine orchestration, Flowable clustering / HA, production monitoring, load testing.
  • Real fact providers: EPIC 1–6 providers currently echo the request (stubs) — wiring them to customer/debt/contract services is future work.
