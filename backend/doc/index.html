1. Architecture du projet

Dept Collector est une plateforme de recouvrement de créances construite en microservices Maven multi-modules : une passerelle (api-gateway, port 8080), une librairie transverse (shared-kernel) et 25 services autonomes (ports 8081+), chacun avec sa propre base PostgreSQL.

ModulePortRôle
api-gateway8080Spring Cloud Gateway — point d'entrée unique
segmentation-service8092Moteur DMN — tables de décision (segmentation / qualification)
workflow-service8094Moteur BPMN — orchestration du processus de recouvrement
flowable-ui (Docker)8090Interface graphique Flowable (Modeler / Task / Admin / IDM)
Autres services8081+customer, debt, contract, payment, legal, notification, …

Multi-tenancy

Chaque requête doit porter l'en-tête X-Tenant-Id. Le filtre TenantContextFilter (shared-kernel) le rend obligatoire et alimente un ThreadLocal (TenantContext). Toute requête Flowable (démarrage de processus, requêtes runtime/historique) est filtrée par ce tenant. Exceptions : /actuator, /swagger-ui, /v3/api-docs et /process-api (voir §6).

2. Contexte métier — le workflow de recouvrement

L'objectif est de qualifier un dossier de recouvrement puis de démarrer automatiquement le bon processus BPMN. La qualification analyse le dossier en 6 étapes (EPICs 1–6) avant de rendre une décision métier (EPIC 7) qui route vers le bon sous-processus (EPIC 8).

Les faits collectés (EPICs 1–6)

EPICVérificationRésultats possibles
1Informations client (nom, CIN/ICE, téléphones, email, adresse, employeur…) CLIENT_INFORMATION_COMPLETE / CLIENT_INFORMATION_INCOMPLETE
2Contrat (numéro, produit, statut, dates, actif/suspendu/résilié) ACTIVE_CONTRACT / SUSPENDED_CONTRACT / TERMINATED_CONTRACT
3Dette (montant, échéances, retards)faits sur l'impayé
4–6Historique de contact, promesses de paiement, relancesfaits de suivi (ex. FIRST_CONTACT)

La qualification (EPIC 7)

Le moteur évalue les cas par ordre de priorité :

1Informations client incomplètesCLIENT_INFO_INCOMPLETETâche « Compléter les informations client »
2Dette déjà payéeDEBT_CLOSEDClôture du dossier (inline)

4Deuxième relanceFOLLOW_UPTâche d'appel téléphonique
5Promesse non respectéePROMISE_BROKENRelance renforcée (escalade)
6Client injoignableINFO_RESEARCHMission de recherche d'informations (inline)
7Retard important, relances sans succèsPRE_LEGALTransfert au service pré-juridique

3. Le processus BPMN (workflow-service)

Deux fichiers sous services/workflow-service/src/main/resources/processes/, auto-déployés au démarrage (aucune étape manuelle) :

  • debt-collection-process.bpmn20.xml — l'orchestrateur, clé de processus debtCollectionProcess.
  • collection-subprocesses.bpmn20.xml — les 6 sous-processus (EPIC 8), chacun étant sa propre définition.
start → validateDebt → segmentDebt → qualificationGateway ─┬─ LEGAL → callLegal → end (route sur ├─ PRE_LEGAL → callPreLegal → end ${qualification}) ├─ PROMISE_BROKEN → callEscalation → end ├─ FOLLOW_UP → callPhone → end ├─ CLIENT_INFO_INCOMPLETE → callUpdateInfo → end ├─ DEBT_CLOSED → closeFile → end (inline) ├─ INFO_RESEARCH → infoResearch → end (inline) └─ défaut (FIRST_CONTACT) → callReminder → end

Les delegates Java

ClasseLiaison BPMNRôle
ValidateDebtDelegate delegateExpression (bean Spring) Validation du dossier (placeholder actuellement)
SegmentDebtDelegate delegateExpression (bean Spring) Le moteur de qualification : (1) résout les faits EPIC 1–6 via CollectionFactsResolver, (2) appelle la DMN du segmentation-service via SegmentationClient, avec repli local (qualifyLocally) si la DMN est indisponible. Pose les variables qualification, qualificationReason, segment (HIGH_RISK/LOW_RISK) et qualificationSource (DMN/LOCAL).
ApplyStrategyDelegate flowable:class (instance par exécution) Chaque sous-processus injecte ses propres littéraux strategy/status/workflow — le comportement par qualification reste déclaré dans le BPMN, pas dupliqué en Java.

Invariants du service

  • Tenancy : chaque opération appelle TenantContext.getRequiredTenantId() ; les processus sont démarrés avec .tenantId(...) et toutes les requêtes Flowable sont filtrées par tenant.
  • Démarrage idempotent (POST /api/v1/workflows/processes) : si une instance active existe déjà pour le même businessKey (= debtId) + tenant, elle est retournée (HTTP 200) au lieu d'en créer une seconde (HTTP 201).
  • debtId est la business key BPMN, injectée aussi comme variable de processus.

4. La décision DMN (segmentation-service)

Les règles de qualification sont externalisées dans une table de décision DMN (debt-segmentation.dmn, sous services/segmentation-service/src/main/resources/dmn/), modifiables sans recompiler le code — c'est l'exigence « règles facilement modifiables via Flowable DMN ».

La chaîne BPMN → DMN

┌──────────────────────┐ POST /api/v1/segmentation/execute ┌───────────────────────┐ │ workflow-service │ ────────────────────────────────────▶ │ segmentation-service │ │ (BPMN, port 8094) │ X-Tenant-Id / X-Correlation-Id │ (DMN, port 8092) │ │ SegmentDebtDelegate │ ◀──────────────────────────────────── │ debt-segmentation.dmn│ └──────────────────────┘ qualification + règles matchées └───────────────────────┘ │ └── si la DMN est injoignable → repli local (qualifyLocally, cas EPIC-7 en ordre de priorité). Le delegate NE LÈVE JAMAIS d'exception sur échec DMN : le processus BPMN continue toujours (qualificationSource = LOCAL).
  • La réponse DMN retourne le segment ET les règles matchées (explicabilité de la décision).
  • Les en-têtes X-Tenant-Id et X-Correlation-Id sont propagés par SegmentationClient.
  • Flowable est volontairement limité à deux services : ne jamais ajouter de dépendance Flowable ailleurs.

5. Intégration Flowable — versions et choix techniques

Les versions utilisées

ComposantArtefactVersionPourquoi
workflow-service flowable-spring-boot-starter-process
flowable-spring-boot-starter-rest		 7.2.0 Moteur BPMN embarqué + API REST officielle (/process-api). Flowable 7.x est la seule lignée compatible Spring Boot 3 / Jakarta.
segmentation-service flowable-spring-boot-starter-dmn 7.2.0 Moteur DMN embarqué pour les tables de décision.
Flowable UI (Docker) image flowable/flowable-ui 6.8.0 Les applications UI (Modeler/Task/Admin/IDM) n'existent plus en 7.x — la dernière version publiée est la 6.8.0.
Pourquoi ne PAS rétrograder le moteur en 6.8 ? Un downgrade a été envisagé (pour aligner le moteur sur la UI) puis abandonné après vérification : Flowable 6.8 enregistre son auto-configuration uniquement via META-INF/spring.factories, un mécanisme supprimé par Spring Boot 3 (remplacé par AutoConfiguration.imports, introduit chez Flowable en 7.0). Avec 6.8 sur le classpath, Spring Boot 3.5 ne créerait aucun bean ProcessEngine/RuntimeService — le service ne démarrerait pas. De plus, 6.8 est basé sur javax.servlet alors que le projet est Jakarta. La seule issue aurait été de rétrograder les 25 services vers Spring Boot 2.7 (EOL) — refusé.

Le compromis retenu

Le moteur reste en 7.2.0 (moderne, supporté) ; la visualisation est assurée par la Flowable UI 6.8.0 en Docker, dont l'application Admin est branchée sur l'API REST du moteur 7.2 (/process-api) — les endpoints REST sont restés stables entre 6.8 et 7.2 pour la consultation (définitions, instances, jobs, diagrammes).

6. Flowable UI — installation et fonctionnement

La Flowable UI tourne comme service Docker dans le compose.yaml racine (image officielle flowable/flowable-ui:6.8.0, port hôte 8090).

ApplicationUsage dans ce projet
Admin ⭐ L'outil principal : pré-connectée au moteur réel de workflow-service via http://host.docker.internal:8094/process-api. Permet de consulter les définitions déployées, les instances en cours, les variables, les jobs/timers et le diagramme du processus.
Modeler Concevoir des BPMN / DMN / formulaires graphiquement. ⚠️ Le bouton « Deploy » déploie dans le moteur 6.8 embarqué de la UI, pas dans workflow-service : pour utiliser un modèle, exporter le XML et le placer dans resources/processes/ du workflow-service.
Task Liste de tâches humaines du moteur embarqué de la UI (pas celui de workflow-service).
IDM Gestion des utilisateurs/groupes de la UI (login admin / test).

Comment la UI atteint le moteur 7.2

┌───────────────────────────────┐ REST (basic auth) ┌──────────────────────────────┐ │ Docker : flowable-ui 6.8.0 │ GET /process-api/repository/… │ workflow-service 7.2 (hôte) │ │ App Admin │ ───────────────────────────────▶│ port 8094 │ │ http://localhost:8090 │ via host.docker.internal │ /process-api (starter-rest) │ └───────────────────────────────┘ └──────────────────────────────┘
  • workflow-service expose l'API REST officielle Flowable grâce à flowable-spring-boot-starter-rest ; sa sécurité propre (FlowableSecurityAutoConfiguration) est exclue pour rester sous la chaîne de sécurité du shared-kernel.
  • L'app Admin ne sait envoyer que du basic auth (pas d'en-têtes personnalisés) : le chemin /process-api a donc été ajouté aux exemptions tenant de TenantContextFilter — les requêtes Flowable portent leur propre dimension tenant.
  • La connexion est pré-configurée par variables d'environnement dans le compose (FLOWABLE_ADMIN_APP_SERVERCONFIG_PROCESS_*). Astuce : le CONTEXTROOT vaut "/" car une valeur vide est refusée par la validation, mais le slash est éliminé à la construction de l'URL — le résultat est bien http://host.docker.internal:8094/process-api.

7. Bases de données — la UI partage-t-elle la base du workflow-service ?

NON — et c'est volontaire. La Flowable UI a sa propre base flowable_ui, distincte de workflow_service. Les deux ne doivent jamais être partagées.

Pourquoi la séparation est obligatoire

Chaque moteur Flowable tamponne sa version de schéma dans la table ACT_GE_PROPERTY (clé schema.version) et la vérifie au démarrage. Le moteur du workflow-service écrit 7.2.0.x ; le moteur 6.8 embarqué dans la UI refuserait de démarrer sur ce schéma « plus récent » (FlowableWrongDbException). Un partage de base est donc structurellement impossible entre une UI 6.8 et un moteur 7.2.

BasePropriétaireContenu
workflow_service workflow-service (moteur 7.2) Tables moteur ACT_* (gérées par Flowable, database-schema-update=true) + tables métier gérées par Flyway (outbox_event…). Jamais de migration Flyway sur les tables ACT_*.
flowable_ui Flowable UI (moteur 6.8 embarqué) Tables du Modeler (ACT_DE_*), IDM (ACT_ID_*), config Admin (ACT_ADM_*) et le moteur 6.8 interne de l'app Task.
segmentation_service segmentation-service (moteur DMN 7.2) Tables DMN + tables métier Flyway.

La base flowable_ui est créée automatiquement par infra/postgres/init-databases.sql à la première initialisation du volume Postgres. La liaison entre la UI et le moteur réel ne passe donc pas par la base de données mais par l'API REST (/process-api).

8. Guide d'utilisation

Étape 1 — Démarrer l'infrastructure

# depuis la racine backend/
docker compose up -d
# démarre : postgres, keycloak, redis, kafka et flowable-ui (8090)

Étape 2 — Démarrer les services Flowable

mvn -pl services/segmentation-service -am spring-boot:run   # DMN  (8092)
mvn -pl services/workflow-service     -am spring-boot:run   # BPMN (8094)
# les fichiers BPMN et DMN sont auto-déployés au démarrage

Étape 3 — Ouvrir la Flowable UI

http://localhost:8090/flowable-ui Connexion : admin / test
  1. Ouvrir l'application Admin (icône engrenage).
  2. Section Process Engine → l'endpoint host.docker.internal:8094/process-api est déjà configuré.
  3. Onglet Definitions : debtCollectionProcess et les 6 sous-processus apparaissent, avec leur diagramme.
  4. Onglet Process Instances : consulter les instances, leurs variables (qualification, segment, strategy…), leur historique et le diagramme d'exécution.

Étape 4 — Démarrer un processus et le voir dans la UI

# chemin démo complet (synchrone, renvoie la qualification calculée)
curl -X POST http://localhost:8094/api/v1/workflows/collection/start \
  -H "X-Tenant-Id: tenant-demo" -H "Content-Type: application/json" \
  -d '{"debtId":"DEBT-1001"}'

# démarrage idempotent (201 créé / 200 déjà existant)
curl -X POST http://localhost:8094/api/v1/workflows/processes \
  -H "X-Tenant-Id: tenant-demo" -H "Content-Type: application/json" \
  -d '{"debtId":"DEBT-1001"}'

L'instance est ensuite visible dans Admin → Process Instances (les processus actuels n'ayant ni tâche humaine ni timer, ils s'exécutent d'un trait : consulter l'onglet historique pour les voir terminés).

Dépannage

SymptômeCause / solution
La UI ne démarre pas au premier docker compose up (erreur connexion DB) Course avec l'initialisation de Postgres au tout premier lancement du volume. Relancer : docker compose up -d flowable-ui.
Admin affiche « engine unreachable » workflow-service n'est pas démarré sur 8094, ou tourne avec un ancien shared-kernel (sans l'exemption /process-api) — redémarrer le service.
400 Missing X-Tenant-Id sur /process-api Ancien code : reconstruire (mvn -pl services/workflow-service -am …) pour inclure le TenantContextFilter à jour.
FlowableWrongDbException dans la UI La UI a été pointée sur workflow_service (schéma 7.2) — elle doit rester sur flowable_ui.

9. API REST du workflow-service (base /api/v1/workflows)

EndpointDescription
POST /collection/start Démarrage synchrone (chemin démo) : exécute le processus de bout en bout et retourne qualification, qualificationReason, segment, strategy, status lus dans l'historique. Toujours 201.
POST /processes Démarrage idempotent : 201 si créé, 200 si une instance active existe déjà pour le même debtId + tenant.
GET …/tasks + POST …/completeTâches humaines actives + complétion.
GET …/historyHistorique du processus (transitions, y compris timers/SLA).
GET …/variablesVariables live d'une instance.
GET …/incidentsJobs en échec avec leurs exceptions.
GET …/deadletter + retryJobs en dead-letter + relance.
GET …/timers + triggerTimers + déclenchement manuel (sans attendre l'échéance).

S'y ajoute l'API REST officielle Flowable (/process-api/**, fournie par flowable-spring-boot-starter-rest) — celle que consomme la Flowable UI Admin. Documentation Swagger du service : http://localhost:8094/swagger-ui.html.
