≈ 30 sec

1. Accroche

On a un problème classique : un dossier de recouvrement de créance ne suit pas un chemin unique. Parfois c'est un simple rappel téléphonique, parfois ça part en contentieux avec un dossier juridique complet, avec plusieurs équipes qui interviennent dans le désordre. Coder ça à la main en Java, avec des if/else partout, ça devient vite illisible et impossible à faire évoluer sans redéployer. C'est exactement le problème que Flowable résout, et je vais vous montrer comment on l'a mis en place sur notre cas réel.

≈ 1-2 min

2. Contexte métier & où les moteurs s'appellent entre eux

Pour les nouveaux arrivants sur le projet : notre plateforme découpe le recouvrement de créances en 25 microservices autonomes, chacun avec sa propre base de données. Le "processus métier" qu'on modélise ici, c'est le parcours d'un dossier de créance depuis sa détection jusqu'à sa clôture — un parcours qui traverse plusieurs de ces services, et c'est précisément ce que Flowable orchestre.

Le processus métier complet, en une phrase : une dette est identifiée → elle est qualifiée automatiquement (quel segment client, quel niveau de risque, quelle action) → un agent humain valide ou corrige cette qualification → le dossier est traité soit par un parcours standard (relance, promesse de paiement), soit par un parcours contentieux (dossier juridique). Rien de tout ça n'est codé en dur dans un seul gros service : chaque étape est déléguée au moteur le mieux adapté, et les trois moteurs Flowable ne vivent pas isolés — le BPMN les appelle explicitement au fil de l'exécution.

Qui appelle qui, concrètement

BPMN → DMN — à l'étape stageRecovery (ou segmentDebt sur l'autre process), le moteur BPMN de workflow-service délègue le calcul de qualification à un service task (StageRecoveryDelegate/SegmentDebtDelegate) qui fait un appel REST synchrone vers segmentation-service, où tourne le moteur DMN. La table de décision répond avec le segment/stage/priorité, et le BPMN reprend la main avec ces variables déjà posées sur le process. SegmentationClient → POST /api/v1/segmentation/execute (fallback local si indisponible)
BPMN → CMMN — quand la porte de stage route vers le cas contentieux le plus lourd (STAGE3_LITIGATION), le BPMN n'essaie pas de modéliser la suite en étapes séquentielles : il délègue à un case CMMN via StartLegalCaseDelegate, qui utilise CmmnRuntimeService pour démarrer une instance de case. Le BPMN reste "en attente" pendant que le case tourne son propre cycle de vie, indépendant, jusqu'à ce que la tâche "Close Case" le termine. CmmnRuntimeService.createCaseInstanceBuilder() — pas d'élément BPMN natif pour ça, d'où le delegate
DMN et CMMN ne se parlent jamais directement — c'est toujours le BPMN qui est au centre et qui décide, à un point précis du process, d'appeler l'un ou l'autre. C'est ce qui rend le système lisible : un seul diagramme (le BPMN) donne la vue d'ensemble de "qui fait quoi, quand".

Pourquoi c'est important à comprendre dès le premier jour sur ce projet : si vous cherchez "où est calculée telle règle métier", la réponse dépend de la nature de la règle — un ordre d'étapes se trouve dans le BPMN, un calcul/seuil se trouve dans une table DMN (segmentation-service), un travail non ordonné avec plusieurs tâches possibles en parallèle se trouve dans le CMMN. Ne cherchez jamais la logique de décision dans le code Java du BPMN — elle est volontairement externalisée dans les fichiers DMN pour pouvoir évoluer sans redéploiement.

≈ 1 min

3. C'est quoi Flowable, en une phrase

Flowable, c'est un moteur d'exécution de processus métier, open source, qu'on embarque directement dans nos microservices Spring Boot — pas un gros outil externe à administrer à part. Le principe : au lieu d'écrire la logique métier en code impératif, on la déclare dans des fichiers — des diagrammes BPMN, des tables de décision DMN, des cases CMMN — et le moteur les exécute, les persiste en base, et nous donne gratuitement l'historique complet de chaque dossier.

Chez nous, ce moteur tourne dans deux services distincts, chacun avec une seule responsabilité :

ServiceMoteur FlowableRôle
workflow-serviceBPMN + CMMNOrchestre le process et pilote les cases juridiques
segmentation-serviceDMNCalcule les décisions métier (stage, priorité, action)

Les deux moteurs communiquent en REST — workflow-service appelle segmentation-service à l'étape de staging, avec un fallback local si le service DMN est indisponible : le process ne tombe jamais en panne à cause d'un service externe injoignable.

≈ 2-3 min

4. Les trois moteurs, un seul dossier

Flowable, ce n'est pas un seul outil, ce sont trois moteurs complémentaires, et c'est ça la vraie force. Chacun résout un problème différent — même dossier, trois logiques.

BPMN

Le chef d'orchestre — ordre imposé

Le BPMN décrit un ordre séquentiel : « d'abord ça, puis ça, puis on attend une validation humaine, puis on route selon une condition ». C'est le squelette du process — étapes, portes de décision (gateways), timers, événements.

services/workflow-service/src/main/resources/processes/banking-recovery-process.bpmn20.xml — process key bankingRecoveryProcess.

DMN

La logique de décision, isolée

Une table de décision : « avec ces données en entrée, quelle sortie ? » — sans coder ça en dur dans le process. L'intérêt majeur : changer un seuil métier (ex. 90 → 75 jours de retard pour déclencher un contentieux) se fait en modifiant une table de décision, pas le diagramme du process ni le code Java. Chaque exécution est tracée individuellement — entrées, règle déclenchée, sortie.

Chaîne de 4 décisions dans segmentation-service : customerSegmentationDecision → collectionStagingDecision → collectionPriorityDecision → collectionActionDecision, orchestrées côté serveur en un seul appel REST pour ne pas multiplier les allers-retours réseau.

CMMN

Le travail non séquentiel — pas d'ordre imposé

Pour la partie qu'aucun organigramme figé ne peut décrire correctement : le travail de dossier juridique. Un case expose un plateau de tâches discrétionnaires que l'équipe peut traiter dans n'importe quel ordre, selon la réalité du dossier. Le case se termine tout seul (sentry de sortie) dès que la tâche de clôture est complétée.

services/workflow-service/src/main/resources/cases/bankingCollectionCase.cmmn.xml — 7 tâches humaines : Investigate Customer, Request Additional Documents, Contact Customer, Request Manager Approval, Send Formal Notice, Escalate to Legal, Close Case.

≈ 1-2 min

5. Notre architecture technique

Quelques détails d'implémentation qui expliquent pourquoi ce système est robuste et pas juste une démo qui tourne par chance.

Multi-tenant sans le tenant natif de Flowable

Chaque requête porte un header X-Tenant-Id obligatoire. Mais le BPMN et le DMN se déploient sur le déploiement "par défaut" de Flowable (sans tenant natif) — sinon le moteur cherche une définition "pour le tenant X" qui n'existe pas et lève une exception. À la place, le tenantId est porté comme variable de process, et chaque requête qui liste des instances filtre explicitement dessus.

Démarrage idempotent

L'identifiant de dette (debtId) sert de business key Flowable. Avant de démarrer un process, on interroge d'abord l'historique (pas le runtime — un process peut déjà être allé plus loin ou être terminé) pour voir si une instance avec la même clé existe déjà. Si oui, on la retourne (HTTP 200) au lieu d'en créer une deuxième (HTTP 201).

POST /api/v1/workflows/banking-recovery/processes
X-Tenant-Id: tenant-demo
{
  "debtId": "TECHLEAD-DEMO-01",
  "customerId": "CUST-01",
  "clientSegment": "ENTREPRISES",
  "overdueDays": 95,
  "totalExposure": 42000
}
→ 201 Created  { "processInstanceId": "...", "created": true }
→ (rejoué)      { "processInstanceId": "...", "created": false }  // 200 OK

Le moteur asynchrone tourne réellement

Le timer de relance n'est pas décoratif : l'async executor Flowable tourne en tâche de fond et déclenche les timers à échéance, sans intervention manuelle. On l'a vérifié en direct — un timer de 30 secondes (calibré pour la démo, 2 jours en production) s'est déclenché tout seul pendant qu'on naviguait dans l'interface, et a fait avancer le dossier jusqu'à l'escalade.

≈ 2-3 min

6. L'exemple pas à pas

Concrètement, voici ce qui se passe pour un dossier réel, du démarrage jusqu'à la clôture.

Démarrage — un appel REST crée l'instance avec un debtId, un client, un montant, un nombre de jours de retard. POST /banking-recovery/processes
Trois étapes automatiques — Extract Irregular Account → Check KYC and Reachability → Stage Recovery File. Cette dernière appelle la chaîne de 4 décisions DMN et fixe les variables stage, priority, action, recoveryTeam. serviceTask × 3 — délégués Spring (StageRecoveryDelegate)
Point d'arrêt — tâche humaine — "Handle Recovery Case", assignée dynamiquement à un groupe candidat selon ${recoveryTeam}. Un agent la réclame et la complète, au clic, depuis Flowable Admin UI. userTask — candidateGroups dynamique + boundary timer P2D (relance SLA)
Le process reprend seul — porte d'escalade, puis porte de stage. Deux issues possibles selon ce qu'a calculé le DMN : exclusiveGateway × 2
Cas léger — recouvrement standard : la porte événementielle attend soit un paiement (message), soit l'expiration d'un timer. Sans paiement à temps → escalade automatique. eventGateway — timer PT30S (démo) / message paymentReceivedMessage
Cas lourd — fort retard + forte exposition : ouverture directe d'un case CMMN pour le passage en contentieux juridique. Sept tâches discrétionnaires s'ouvrent d'un coup, aucun ordre imposé. startLegalCase → CmmnRuntimeService.createCaseInstanceBuilder()
Clôture — que ce soit côté BPMN (paiement reçu / escalade) ou côté CMMN (tâche "Close Case" complétée, qui déclenche la sentry de sortie et termine tout le case d'un coup), tout est visible et historisé.
✅
Tout ce parcours est pilotable et observable entièrement depuis Flowable Admin UI — assignation, complétion de tâche, relecture du diagramme à chaque étape, consultation des exécutions DMN, suivi du plateau CMMN — sans une seule commande terminal après le démarrage initial.
≈ 1-2 min

7. Pourquoi Flowable est la bonne solution ici

Trois raisons concrètes, pas juste "c'est un bon outil".

1

Un workflow hybride par nature

Une partie strictement séquentielle (BPMN), une partie purement décisionnelle (DMN), une partie totalement libre (CMMN). Peu d'outils couvrent les trois avec le même moteur, la même base, la même API.

2

La traçabilité est gratuite

Chaque tâche, chaque décision, chaque timer déclenché est historisé automatiquement — rien codé pour ça. Pour un métier réglementé comme le recouvrement, c'est un audit trail livré out-of-the-box.

3

Séparation des responsabilités

La logique de décision métier vit dans des fichiers DMN modifiables sans redéploiement Java. Le code applicatif ne fait que l'intégration technique — les règles métier évoluent sans toucher au code.
